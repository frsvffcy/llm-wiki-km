## Prerequisites (exact-artifact dogfood, Refs #454 §D)

- Use the exact `v0.1.1` candidate JAR (verify `*-manifest.json` `sourceCommit` + `artifactSha256`).
- Clean application state: fresh temp install root, no reused `test/` data, no pre-seeded prompt / DB / vault.
- Start: `java -jar <candidate>.jar` on loopback only; confirm `GET /api/v1/system/status` is `NOT_INITIALIZED`.
- Create a fresh workspace via Browser Workspace view; confirm `document-analysis.md` is auto-provisioned
  (via `GET /api/v1/analysis/readiness` `promptStatus=READY`, never by harness `Files.write`).
- Do not modify DOM via devtools, do not edit SQLite, do not write canonical vault to skip Proposal / Draft / Publish.

## Steps

```text
Workspace → Inbox → upload → extract → Analysis readiness → Review / Wiki / Ask navigation
```

1. **Workspace**: create / switch workspace via `#/workspace`; confirm active root is the fresh temp root;
   switching clears and re-fetches workspace-scoped state.
2. **Inbox empty**: with zero documents, confirm exactly one empty-state panel is visible;
   with devtools assert the list container is `hidden` (mutually exclusive, #450).
3. **Upload**: single + batch upload deterministic fixture (or exact sentinel file); partial failures render honestly.
4. **Extract**: run extraction; confirm row shows `文件狀態：待處理` + `抽取狀態：已抽取`
   (dual badges, `data-status="PENDING"` + `data-parse-status="PROCESSED"`, #451);
   button on a `PROCESSED` row reads `重新抽取`, on never-extracted reads `執行抽取`.
5. **Filter**: `status=` offers only lifecycle (`PENDING` / `DUPLICATE`); extraction states filter via
   `parseStatus=` only; extraction success keeps lifecycle deletable.
6. **Non-empty hides empty**: after upload, confirm empty-state panel is `hidden` and list has rows
   (never both visible, #450); check Inbox + Wiki + Review surfaces share the same authority.
7. **Analysis readiness**: confirm analysis readiness presentation is readable (`READY` vs typed
   `MISSING` / `INVALID` + repair hint); failure never masquerades as overall app failure.
8. **Navigation**: from Inbox reach Review (`#/review`), Published Wiki (`#/wiki`), Ask (`#/ask`);
   each view loads without console errors and preserves workspace scope.

## Recording evidence

- Record: candidate filename + `artifactSha256` (first 12) + `sourceCommit` (first 12) + browser + OS.
- For each step: PASS / FAIL + one-line observation (no full DOM dump, no secrets, no absolute paths beyond redacted root label).
- Any supported-flow blocker → immediately file a corrective Issue and block publish (no manual DB / prompt / vault fix to force green).
- Attach the checklist outcome to the release evidence (alongside `target/release-evidence/` JSON reports).

## Challenge self-check (must all be NO)

1. Did the smoke use an old `v0.1.0` JAR while claiming #448 / #450 / #451 verified? → must be NO.
2. Was `document-analysis.md` hand-written by the harness after workspace create? → must be NO.
3. Did the smoke only check HTTP 200 without confirming mutually-exclusive UI state / dual projection? → must be NO.
4. Was any DOM / DB edit used to fake state? → must be NO.
5. Was live provider success treated as deterministic correctness proof? → must be NO.
6. Did any token appear in `ps` / log / report / screenshot / artifact? → must be NO.
