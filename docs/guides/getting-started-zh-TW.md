# llm-wiki-km 快速入門

> 狀態：`CURRENT`。給第一次使用 llm-wiki-km 的人；約 5–10 分鐘可完成第一個工作區、匯入文件、閱讀 Wiki 並提出一個問題。
>
> 本指南是 learning aid，不是 API 或資料庫契約。可複製的 endpoint、狀態值和設定鍵仍以目前程式碼與測試為準。

## 1. 先理解它是什麼

llm-wiki-km 是**以本機為優先的個人知識庫**。你把文件放進工作區的收件匣，系統抽取並索引內容，再讓你閱讀已發布的 Wiki、檢視引用來源、提出有依據的問題，並透過「提案 → 草稿 → 人工審核 → 發布」流程把整理後的內容寫回知識庫。

Ask 的回答是暫時結果（ephemeral），不會自行修改 Wiki。任何要成為持久知識的內容，都必須經過人工治理流程。

## 2. 五個核心概念

| 概念 | 你可以把它想成 | 主要用途 |
| --- | --- | --- |
| 工作區 | 一個獨立的知識根目錄與設定 | 隔離不同主題、資料與狀態 |
| 收件匣 | 待處理文件的入口 | 上傳、重新掃描、檢視抽取狀態 |
| Wiki | 已經發布、可閱讀的權威知識 | 閱讀頁面、前往提問或檢視來源 |
| 提問 | 對目前工作區做一次有依據的檢索與回答 | 快速找到答案與引用來源 |
| 審核／品質 | 持久化內容的治理與健康檢查 | 審核提案、管理草稿、處理診斷項目 |

「檢視器」則是唯讀的診斷畫面：它讓你看到檢索候選、融合順序、權威驗證與來源片段，不會重新寫入資料。

## 3. 啟動與開啟畫面

先確認已安裝 Java 21 與 Maven 3.9+，在 repository 根目錄執行：

```bash
mvn spring-boot:run
```

接著用瀏覽器開啟 <http://127.0.0.1:8765/>。預設只綁定本機；瀏覽器只呼叫本機 REST API，不直接碰 SQLite、檔案系統或 provider 金鑰。

第一次開啟時依序會看到：

1. **工作區**：建立或切換知識根目錄，並檢視目錄結構是否就緒。
2. **Wiki**：閱讀已發布頁面；沒有頁面時會顯示空狀態。
3. **收件匣**：上傳單檔／多檔、重新掃描、檢視文件與抽取狀態。
4. **提問**：選擇檢索範圍、取得回答、檢視引用來源；可將回答明確轉成提案。
5. **檢視器**：檢查一次檢索的候選與來源定位。
6. **審核**：處理提案、建立草稿、預覽／檢視差異，最後由人工作出發布決定。
7. **品質**：唯讀檢視 Vault Lint 診斷項目，必要時把合格項目送入修復提案流程。

## 4. 5–10 分鐘的第一個流程

### 步驟一：建立工作區

在「工作區」輸入名稱與本機絕對路徑，例如 `/Users/you/knowledge-root`，按「建立工作區」。系統會建立可重建的 `inbox/`、`archive/`、`vault/`、`data/`、`config/`、`logs/`、`temp/` 目錄；不會刪除既有內容，也不會把瀏覽器直接連到檔案系統。

### 步驟二：放入文件

切到「收件匣」，上傳一個 PDF、Markdown 或其他支援的文件。需要時按「重新掃描收件匣」。每筆文件同時有兩種狀態：生命週期狀態（例如 `PENDING`、`DUPLICATE`）與抽取狀態（例如 `PROCESSED`、`FAILED`、`NEED_OCR`）。抽取完成後可開啟「抽取內容預覽」確認內容。

### 步驟三：閱讀或提問

若工作區已有已發布 Wiki，先到「Wiki」閱讀；否則到「提問」以目前已索引的來源文件取得回答。問題越具體，越容易得到可驗證的引用。回答下方的「引用來源」可以打開來源定位；若內容已變動，系統會標記為與權威狀態不一致，不會顯示過時內容。

### 步驟四：把好答案送進治理流程（可選）

Ask 的回答不會自動寫入知識庫。確認回答與引用後，按「轉為提案」，再到「審核」：

1. 檢查提案摘要、目標與證據。
2. 將提案送入適當的審核狀態。
3. 由已核准的提案建立 Wiki 草稿。
4. 先預覽與檢視差異，再由人工作出「發布」決定。

發布後回到「Wiki」閱讀新的權威頁面。任何階段若工作區切換，畫面會清空並重新讀取新工作區的狀態。

## 5. 常見狀態怎麼看

| 畫面狀態 | 意義 | 建議動作 |
| --- | --- | --- |
| 空白／尚無資料 | 尚未建立工作區、沒有文件或沒有已發布頁面 | 先建立工作區、上傳文件或完成審核 |
| 載入中／處理中 | 後端正在讀取或執行非同步作業 | 等待後重新整理，不要重複送出 |
| 已就緒／有依據 | 目前資料可使用，回答有引用支持 | 檢查引用來源並決定是否建立提案 |
| 部分完成／已降級 | 某個可選投影或文件項目失敗，但基礎能力仍可用 | 閱讀診斷，必要時重建或修復 |
| 錯誤／無法使用 | 請求被拒絕、服務未設定或資料不再符合權威狀態 | 依訊息的下一步處理；不要猜測或繞過治理流程 |

系統會把公開錯誤簡化為穩定的錯誤代碼與安全說明；絕對路徑、SQL、token、stack trace 與 provider 原始回應只留在伺服器端紀錄。

## 6. 資料與隱私邊界

- 工作區內容、SQLite 中繼資料與可重建投影預設留在本機。
- 瀏覽器不持有 provider 金鑰，也不直接呼叫 LLM／embedding provider。
- Ask 或文件分析若啟用遠端服務，送出的資料範圍由後端設定與 UI 的 provider egress 提示決定；請在啟用前確認服務提供者、傳輸方式與資料類型。
- 遠端 HTTP（非 HTTPS）只有在明確的後端 opt-in 下才可能使用，不適合作為生產設定。
- Graph／向量等投影是可刪除、可重建的衍生資料，不是權威知識來源；SQLite 與 `vault/`／`archive/` 的治理邊界仍是準則。
